# Decisions

以下为 2026-10-02 方案推荐，尚不代表用户已确认产品限制。

## R2 密文中转

- 选择：浏览器加密与解密，R2 仅存私有密文对象，Pages/Hono 管理权限。
- 理由：支持异步接收，复用现有 Cloudflare/D1 栈；无需双方同时在线。
- 备选：WebRTC + 信令/TURN，后续实时直连场景再评估。

## 长随机配对码与用途隔离

- 选择：26 位 Base32；locator / 接收 authSecret / wrapKey 分域派生；服务端不接收原始配对码。
- 理由：提供 130 bit 熵，避免短口令离线猜测和 salt 检索循环。
- 备选：6～8 位短码必须 PAKE；当前不自行实现密码协议。

## 一块一个对象

- 选择：8 MiB 独立 AES-GCM 块与私有 R2 对象；固定 key 条件写入，不允许覆盖。
- 理由：首版续传/幂等/失败补偿简单，无 multipart complete 和 Range 容器耦合。
- 代价：对象数和操作费增加；高吞吐后再做预签名 multipart。
- 历史：上次中断前讨论过单对象 multipart 草案，未落盘；本轮技术评审改为上述方案。

## 可恢复的单接收会话

- 选择：open 不消耗名额；本地解密后 claim；租约内多次 GET/重试，ack 后 consumed。
- 理由：避免错误码、回包丢失或断网导致文件永久不可领取。
- 代价：不能承诺只存在一个文件副本；过期租约允许重新接收。

## 独立 Cron Worker

- 选择：Pages 处理请求，另外部署 cleanup Worker 并配置 R2 生命周期兜底。
- 理由：不将请求内 scheduled 函数误认为平台定时任务；业务过期和物理删除分开。
- 代价：新增部署资源；D1 与 R2 补偿清理必须可重试。

## 2026-10-02 - 新增 WebRTC 直连备选

- Decision: 可增加 WebRTC DataChannel 模式；配对码只用于信令房间发现，文件仍在浏览器端加密/分块，正常路径不写 R2。
- Rationale: 传输数据直接从发送端到接收端；R2 的 10 GB-month 是存储额度，不是出网/传输额度，因此是否采用 WebRTC 应由在线约束和复杂度决定，而不是只看“10 GB”。
- Alternatives: R2 中转保证异步接收；TURN 兜底保证连通性但会产生实时服务流量。
- Consequences: 发送和接收必须同时在线；需要 ICE/STUN/TURN、信令、DataChannel 背压、断线重连和浏览器保存适配。不能承诺所有连接都直连。

## 2026-10-02 实现决策

- 复用 D1 短期轮询信令，避免新增部署服务；仅文件字节走 WebRTC。
- 恢复以接收端写入位置为准，保存 ACK 丢失不会重复写；串行接收队列避免异步消息竞态。
- 最终 saved 丢失时保留完成结果两分钟，重新配对代际内幂等回应；Blob 数据准备完毕与下载完成区别通过产品文案表达。
- 保存 picker 必须由独立按钮点击触发；用户取消不静默切换内存下载。
- 不自动登录 Cloudflare 或写远程资源；只读 whoami 确认未登录，先完成源码、运行说明和本地验证。
